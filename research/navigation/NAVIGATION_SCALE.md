## 1. Исходный сценарий, а не условный goto

`Scripts/Level1.scc:228–237`:

```text
Click 0 Botl Botl
{
  Case 0
   Goto 660 480
   StartW Takedr1
   Setxy 670 477
   Addtol 1
   State Botl 1
  Break
}
```

Между Goto и Setxy находится **полная ожидаемая анимация** `Takedr1`, а не три пикселя доведения в следующем тике. `Goto` (opcode 2) вызывает `0x409964`, ждёт `Scene+0x72e>0`, затем `StartW` ждёт inactive анимации. `Setxy` (opcode 6) исполняется без ожидания: применяет Stop6, очищает image-cache и вызывает `0x409708(scene,670,477,1)`. Адреса executor: запуск маршрута `0x40606e–0x406086`, ожидание `0x40603f–0x406069`, Setxy `0x40629b–0x406334`; полное dossier уже находится в `../scc/evidence/0x405e5c.json`.

Исходная позиция при клике не зашита в событии. Для воспроизводимого примера взята `(1199,524)` из `Init`, строка 140; это условие офлайн-проверки, не доказательство, что игрок всегда нажимает бутылку именно оттуда. Проверен также старт `(250,450)` из Portal.

Ресурсы Level1:

```text
Back BACKGRD\scn_37.tif
Mask Masks\scn_01_1.tif
Focus 120 1 1
Anim 12 Takedr1 Casm XSH\SCN_37\step_02.mult
```

Разные номера `scn_37` и `scn_01_1` — реальные имена, не повод подменять маску. Найденные background и mask оба **1736×600**.

## 2. Данные сцены и чтение маски — CONFIRMED (static)

| Scene offset | Значение |
|---|---|
| `+0x705` | указатель на raw grayscale scanlines маски |
| `+0x716`, `+0x71a` | логические целочисленные X/Y героя в пикселях сцены |
| `+0x71e` | F, первый float Focus |
| `+0x722` | K, множитель глубины, второй float Focus |
| `+0x726` | M, множитель масштаба, третий float Focus |
| `+0x72a` | поле дистанционных меток `uint16[W*H]` |
| `+0x72e` | число записей построенного пути / ненулевой признак работы |
| `+0x732` | убывающий индекс пути при движении |
| `+0x75e`, `+0x762` | W/H фона сцены, не размеры viewport |
| `+0x766`, `+0x76a` | экранный offset X/Y; обычный scroll меняет X |
| `+0x76e` | объект Mainhero |

`0x405a44`: W/H берутся из фонового объекта (`0x405a95–0x405aa9`), выделяется `W*H*2` байт под метки (`0x405ac3–0x405ad8`). Маска не задаёт отдельную уменьшенную навигационную сетку: размеры фоновой сцены используются для её индексации. На данном ресурсе размеры совпадают; проверку несоответствия в этом пути не обнаружено.

`Mask` → `0x405a08`: выключить surface-conversion через `0x401c6c(0)`, загрузить TIFF, включить обратно, записать `resource+0x10` в `Scene+0x705` (`0x405a37–0x405a3a`). `0x401728` получает TIFF tags, читает scanlines по порядку (`0x40183b–0x401858`); при отключённой конверсии сохраняет raw bytes (`0x4019f7–0x401a03`). Значения не извлекаются из RGB screenshot, не нормализуются по ICC и не являются alpha канала MULT.

`Focus` в парсере `0x406ab7–0x406ad7` читает `%f %f %f` непосредственно в три поля выше. Имя определяется ранее установленным SCC hash-dispatch, ветка `0x14192`.

`0x405924` возвращает значимый **AL**, не весь EAX:

```c
q(x,y) = inBounds(x,y) ? uint8(255 - mask[y*W+x]) : 0;
walkable(x,y) = q(x,y) != 0;
```

Инструкции `0x405949–0x40595e`: row offset, загрузка pointer, `MOV AL,0xff`, `MOV DL,[...]`, `SUB AL,DL`. Белый **255 запрещён**; любой `0..254` проходим. Никакого threshold по тёмному цвету, маски радиуса героя или проверки его прямоугольника в исследованном маршрутизаторе нет. Старшие байты EAX после возврата не очищены: использовать весь EAX как q — ошибка.

## 3. Построение маршрута — CONFIRMED (static)

Цепочка: `Goto → 0x409964 → 0x409874 → 0x408dc4`.

`0x409964` очищает оба счётчика (`0x40997f–0x409985`), корректирует локальную копию цели, затем передаёт в построитель адрес текущей позиции героя и исправленную цель (`0x409999–0x4099a5`). Возвращает `pathCount != 0`, не «цель точно достигнута».

`0x408dc4`:

1. Заполнить `uint16[W*H]` значением `0xffff`; метка старта 0.
2. Кольцевая **FIFO**, capacity `0x1130=4400` пар int. Buffer pointer `0x46878c`, tail `0x468790`, head `0x468794`. Это не priority queue и не A*.
3. Из извлечённого узла посетить соседей в порядке **D, U, R, L, RD, RU, LU, LD**. Для первых четырёх candidate label = current+2, для диагоналей current+3. Улучшение только строго `<`; улучшенный узел добавляется снова.
4. Проверяется только `q` пикселя назначения. Соседние ортогональные клетки при диагональном ходе не проверяются: corner cutting разрешён.
5. Остановить распространение сразу при извлечении цели из FIFO, либо при пустой очереди. Нельзя заменять это гарантированно оптимальным Dijkstra: веса разные, приоритетной очереди нет, выход ранний.
6. Если метка цели осталась `0xffff`, путь не формируется. Иначе восстанавливать **от цели к старту**, каждый раз выбирая минимальную метку среди восьми соседей (не minimum `label+edgeCost`). Tie-order: **D, U, R, L, RD, LD, RU, LU**. Используются строгие `<`.
7. Сначала выбрать соседа, затем записать его в глобальный массив `0x46179c + i*8`; Y по `0x4617a0+i*8`. Поэтому **цель в массив не входит, старт входит последним**. Запись и увеличение count: `0x4096a0–0x4096bd`. При start==target count=0, wrapper возвращает false.

Нет найденного сглаживания в waypoint-сегменты, line-of-sight shortcut, navmesh, графа Portal или маршрутизации по Active/Object. Геометрия маршрута в этих функциях — raw mask + W/H + текущая позиция + целевая позиция; `Focus`, MULT, Light и другие объекты в построении меток не участвуют. Portal используется upstream как источник координат перехода, не как ребро навигационного графа.

Оригинальные ограничения: 16-битные метки, фиксированная очередь; совпадение head/tail вызывает `0x440908`. Обратный проход читает соседние метки без bounds check; явной проверки ёмкости глобального массива пути в рассмотренном append нет. Проверочные сценарии не доходят до этих пределов. Офлайн-probe ставит собственные guards и не воспроизводит повреждение памяти.

## 4. Недостижимая цель: два разных случая

### Пиксель запрещён / вне границ

`0x409874` не проверяет связность со стартом. Если mask pointer есть, перебирает radius `r=0..W-1`, angle index `k=0..19`:

```text
a = float32(k * 2π * 0.05)
x' = trunc(x + r*cos(a))
y' = trunc(y + r*sin(a))
if y' > 0 && q(x',y') != 0: accept and overwrite point
```

Первый принятый образец выигрывает. Это **20 лучей с шагом 18°**, а не полный Euclidean nearest-neighbor и не вертикальное сканирование. Даже исходная допустимая точка с Y=0 не принимается на radius=0 из-за отдельного `y'>0`. Радиус ограничен W, не диагональю сцены. При отсутствии mask либо подходящего образца — false.

Псевдокод Ghidra здесь потерял FPU умножение на radius и прибавление исходной координаты. Доказательство брать из инструкций: X `0x4098c5–0x4098d1`, Y `0x4098ea–0x4098f7`. Cos wrapper `0x43cbb4→0x43ce20` (CL=2), sin `0x43d16c→0x43ce1c` (CL=0); shared body при нуле возвращает cos=1, sin=0. `0x43cf34` принудительно ставит rounding-control `0x0c00`, то есть **trunc toward zero**, вопреки слову ROUND в декомпиляции.

Реальная запрещённая Portal-точка `(1400,280)`, pixel=255: офлайн-поиск выбирает `(1396,269)`, r=11, k=14. От `(670,477)` до исправленной цели строится путь 844 записи. Другие оригинальные запрещённые координаты `(110,330)` и `(118,340)` также проверены; результаты находятся в JSON. Точная побитовая идентичность Python libm с оригинальными software-trig/x87 на граничных значениях **не заявлена**.

### Пиксель проходим, но компонент недостижим

После выбора q!=0 построитель может не достичь цели: метка `0xffff`, count остаётся 0. **Повторного поиска ближайшей точки именно в достижимом компоненте нет**, выбора лучшей достигнутой границы тоже нет. SCC увидит отсутствие работающего пути. Обычный бутылочный список затем всё равно продолжит `StartW Takedr1` и `Setxy` после своего yield/resume: Goto не выбрасывает исключение и не отменяет весь список. Специальная skip-ветка для следующего `StartW Speak` здесь не применима.

На оригинальной `Scn_01_1.TIF` все **197165** проходимых пикселей образуют один 8-связный компонент. Поэтому disconnected-case на этой сцене не выдаётся за наблюдавшийся: он проверен отдельно на малой искусственной маске с изолированной проходимой целью. Это control-flow проверка восстановленного алгоритма, не запуск Agent.exe. При полном отсутствии допустимых образцов счётчики также остаются нулевыми; `Setxy` вызывает snap, но игнорирует его false — нельзя обещать корректную позицию после неуспешной коррекции.

## 5. Скорость и перемещение

Источник времени найден: `0x40f484` вызывает импорт `KERNEL32.GetTickCount` (`0x40f48c`), передаёт EAX через EBX в `0x40c974` (`0x40f4fb–0x40f4fd`), далее `0x40a76c → 0x4099c0`. Время — **миллисекунды**, а не номер кадра MULT.

При первом update нового пути `remaining=count`, сбрасывается история направлений, `lastTime=now`; в этот вызов движение не начинается. Далее при `dt=now-lastTime >= 15`:

```text
s = float32(scale(currentX,currentY))
advance = max(1, floor(dt * 0.25 * s * directionFactor[direction] + 0.5))
remaining -= advance
if remaining <= 0:
    remaining = count = 0
    switch to Stop<direction>, apply frame, refresh image/placement
else:
    position = reversePath[remaining]
    update direction, scene crossing events, Walk<direction>, image/placement
    lastTime = now
```

Адреса: threshold `0x409b48–0x409b55`; scale и advance `0x409b5b–0x409bcf`; count clearing `0x409be8–0x409bf2`; чтение точки **только в nonterminal branch** `0x409c88–0x409cb4`; финальный placement `0x409c6a–0x409c7b`, обычный `0x409eb4–0x409ed6`.

`0x43cf00` делает floor через `FRNDINT` с RC=down (`CH=4`, helper `0x43d140`), затем `0x43cf34` переводит результат в int с trunc. Поэтому для положительного advance это `floor(value+0.5)`, не банковское округление.

Таблица float32 по `0x444a24`: `[1,0.7,1,0.7,1,0.7,1,0.7]` (0.7 хранится как `0x3f333333`). Это компенсация диагонального хода: один диагональный элемент пути геометрически длиннее осевого. Номинально по оси ≈`250*s` px/s, по диагонали каждая координата ≈`175*s` px/s; квантование, повороты и конечный остаток меняют наблюдаемую скорость. Скорость считается по **числу pixel-path entries**, не по меткам 2/3, не через velocity vector и не по длительности шага MULT. Большой dt пропускает много точек; отдельного clamp в этой ветке нет. Не выполненный до 15 ms update не сбрасывает lastTime.

Направление: `atan2(oldY-newY,newX-oldX)`, отрицательный угол привести к `[0,2π)`, умножить на `4/π`, округлить `floor(+0.5)`, modulo 8. 0=вправо, 1=вправо-вверх, 2=вверх, 3=влево-вверх, 4=влево, 5=влево-вниз, 6=вниз, 7=вправо-вниз. Для переключения нужны три одинаковых кандидата подряд; при первой выборке история инициализируется этим кандидатом. Advance использует ранее выбранное направление, а не вычисленное после нового перемещения.

`Mainhero.scc` задаёт Walk0/2/4/6 rate32, диагональные rate36. Эти числа управляют отдельными кадровыми таймерами (`1000/rate`, ранее доказано в SCC_RUNTIME), **не прямо скоростью пути**. На тике сначала SCC, затем анимации, затем движение (`0x40a76c`). Смена Walk вызывает применение кадра через `0x405064(...,-1)`.

### Конец пути не равен присваиванию цели

Когда remaining становится <=0, оригинал не читает ни target, ни path[0], а повторно размещает героя в **предыдущей текущей позиции**. В самом массиве target тоже отсутствует. Следовательно, визуально/логически остановка обычно происходит рядом с целью, с остатком, зависящим от dt; безусловного точного snap-to-target в `0x4099c0` нет.

Синтетические постоянные dt на реальном маршруте от Init (исходное направление 0, без сторонних crossing handlers): dt=15 → `(662,482)`, dt=16 → `(664,484)`, dt=33 → `(666,486)`, dt=100 → `(671,491)`. Это демонстрационные **офлайн-replay**, не измеренные позиции Windows-игры. Они показывают, почему нельзя проверять завершение SCC условием `position==GotoTarget`.

## 6. Глубина и перспектива

`0x405968`:

```text
q = sampleMask(x,y)
z = q != 0 ? floor(q * K + 0.5) : -1
```

`0x4059c0` возвращает через **ST0**:

```text
scale = z >= 0 ? F / (F + z) * M : -1.0
```

Адреса: `0x405994 FILD`, `0x405997 FMUL [scene+0x722]`; `0x40599d FADD 0.5`. Формула масштаба: `0x4059e8 FILD z`, `0x4059eb FADD [scene+0x71e]`, `0x4059f1 FDIVR [scene+0x71e]`, `0x4059f7 FMUL [scene+0x726]`. Гидра ошибочно показывает void и пустой return: здесь решают инструкции и чтение ST0 вызывающими функциями.

`0x409708` записывает z в `hero+0x108` (`0x409776–0x40977c`) и scale в оба float `hero+0x27f/+0x283` (`0x409793–0x40979f`). `0x40868c` делает то же при входе в сцену. Comparator `0x40a4ac` возвращает `abs(rhs.depth)-abs(lhs.depth)`, `0x40a4dc` сортирует список объектов перед рисованием: большие abs(depth) раньше, меньшие позже. Так маска задаёт **порядок наложения героя среди сценовых объектов**, а не только размер. Это painter order, не найденный per-pixel Z-buffer.

Для `Focus 120 1 1`: `z=255-pixel`, `s=120/(120+z)`. Более светлый допустимый пиксель → меньше z → крупнее герой, быстрее продвижение по сетке и иной sort key. Значение 255 отдельно запрещает ход и даёт sentinel -1.

На Y=480 есть разные значения: X=100/250/800/1200 → pixel242, z13, scale≈0.902256; X=660 → pixel241, z14, scale≈0.895522; X=500/1000 запрещены. Значит, глобальная формула `scale(y)` несовместима с ресурсом: требуется **sample(x,y)**.

## 7. Мир → координаты объекта → экран

«Мир» навигации — 2D canvas сцены 1736×600 с началом слева сверху, X вправо, Y вниз. Перспективный z не проецирует X/Y через 3D matrix: он влияет на scale/скорость/sort order. Объектный/MULT space центрирован, Y вверх.

`0x409708` после snap, z и scale:

```text
hero.objX = worldX - trunc(W/2)
hero.objY = trunc(H/2) - worldY + imageHeight * scale / 2
hero.scaleX = hero.scaleY = scale
```

При отсутствии текущего image используется fallback height=250 (`0x4097cd–0x409808`); иначе height из image header +0x0c (`0x40980a–0x409844`). Здесь учитывается **высота растра**, не обнаруженный отдельный bone/pivot. Тем самым логическая позиция примерно совпадает с нижним центром изображения, не его центром.

Renderer `0x404974`, параметры от `0x40a76c:0x40a831–0x40a849`, получает размеры **сцены** и scroll отдельно:

```text
centerX = trunc(trunc(W/2) + objX - scrollX)
centerY = trunc(trunc(H/2) - objY - scrollY)
left   = centerX - floor(imageWidth  * scaleX / 2)
top    = centerY - floor(imageHeight * scaleY / 2)
right  = centerX + ceil (imageWidth  * scaleX / 2)
bottom = centerY + ceil (imageHeight * scaleY / 2)
```

Позиционный переход: `0x404a46–0x404a92`; bounds `0x404a95–0x404b84`. Дальнейший cull — по viewport 800×600. Float32 storage и целочисленные округления допускают однопиксельные отличия от непрерывной формулы; не заменять всё одним CSS transform без такого контракта.

Для обычного героя непрерывное сокращение даёт `screenFoot≈(worldX-scrollX,worldY-scrollY)`, `screenCenter≈(worldX-scrollX,worldY-scrollY-h*s/2)`. Из 1736×600 в 800×600 сцена не ужимается целиком. `0x4087ec` меняет горизонтальный scroll, ограничивая диапазоном `[0,W-800]`, реагируя на выход героя из центральной полосы между X=200 и X=600. Есть отдельная ветка scripted scroll с шагом 10. Y автоматически тем же способом не скроллится.

### Почему MULT нельзя всегда пропускать через эту формулу

Как установлено в MULT_FORMAT, если координаты записи MULT не оба нулевые, renderer `0x404a06–0x404a40` заменяет objX/objY и **сбрасывает scaleX/Y в 1**. Walk0 содержит 24 нулевые позиции, сохраняет размещение навигацией. Но `Takedr1/Step_02.MULT` содержит 52 собственных позиции Mainhero: например, кадр1 `(-206.3611603,-48.3000107)`, растр69×239; кадр52 `(-191.9026031,-48.5889854)`, растр67×237. Это анимационное размещение в object space, не маршрутные точки и не абсолютные координаты ног. Во время pickup герой управляется ими, а после `StartW` Setxy возвращает stop-позу, nav-позицию, глубину и perspective scale.

Для `Setxy 670 477` Stop6 имеет реальный растр **127×278**, координаты MULT `(0,0)`. Pixel маски241, z14, `scale32≈0.8955224156`, objX=-198, objY≈-52.52238464. При scroll=(0,0) renderer получает center=(670,352), bounds=(614,228,727,477). При ненулевом scrollX X-границы сдвигаются на него. Это воспроизводимый числовой пример, а не предполагаемый screenshot оригинала.

## 8. Роль Masks\Scn_01_1.TIF — итог

**Сочетание всех трёх функций:**

1. **Навигация:** pixel255 непроходим; прочие значения допускают pixel-grid routing и радиальную коррекцию.
2. **Перспектива:** обратная яркость превращается в z, затем в `F/(F+z)*M`; этот scale также меняет темп продвижения.
3. **Глубина:** z назначается `hero+0x108` и участвует в сортировке героя относительно других объектов.

Это не три независимых канала: используется один grayscale byte. Не подтверждены физический Z в единицах сцены, 3D геометрия пола или per-pixel occlusion mask; такие интерпретации не нужны для восстановленных потребителей.

Оригинальная маска: 52458 bytes, TIFF little-endian, **8-bit grayscale, LZW, horizontal predictor2, 150 strips по 4 строки**, Photometric=MinIsBlack. SHA-256 `7b003b156241c5c333e67ceb7d0e2243a98ba1132233ecbbfcd347436817ae7e`; decoded scanlines SHA-256 `bdb0d4a7c7b05e13ad2c89a05d6f38454b21ffc9fa86999146fe29308aa3dd20`. Из 1041600 пикселей 844435 запрещены, 197165 проходимы, все в одном 8-связном компоненте.

Оставшиеся границы: нет динамического differential trace Agent.exe; точный software-trig/x87 и renderer sampling/blending не эмулированы; Python float/libm не эталон всех FPU границ.
