## 2. Контейнер — CONFIRMED

Все числа little-endian. Структуры упакованы: поля `uint32` внутри записи часто не выровнены. Нельзя использовать обычное выровненное отображение C-структуры.

| Смещение | Размер | Содержание | Статус |
|---|---:|---|---|
| `0x0000` | 4 | Число временных шагов `frame_count` | CONFIRMED |
| `0x0004` | 4 | Поле, совпадающее с числом используемых элементов палитры | Значения подтверждены; семантика — HYPOTHESIS |
| `0x0008` | `0x3FF8` | 4094 четырёхбайтовые записи палитры | CONFIRMED |
| `0x4000` | переменный | `frame_count` последовательных временных шагов | CONFIRMED |

В каждом временном шаге:

```text
uint32 object_record_count
ObjectRecord records[object_record_count]  // переменная длина каждой записи
```

В файле нет обнаруженной таблицы абсолютных смещений кадров: индекс строится при загрузке последовательным проходом. Число объектов в шаге может быть нулевым. Не следует сводить MULT к одной картинке на кадр: среди данных встречаются до 23 записей объектов в одном шаге.

Доказательство: `FUN_0040c094` (`ev_9eb3df536f513e5648285b121b527f89154821c11fa838454ca2b311d8465549`):

```c
count = *file;
frame = (uint32_t *)((uint8_t *)file + 0x4000);
for (i = 0; i < count; i++) {
    index[i] = frame;
    record = (uint8_t *)(frame + 1);
    for (j = 0; j < *frame; j++)
        record += read_u32(record + 0x36);
    frame = (uint32_t *)record;
}
```

Это нормализованный пересказ псевдокода, не исходный код игры. Исходное представление Ghidra сохранено в Evidence.

Назначение верхнего уровня как временных кадров подтверждает `FUN_00405064` (`0x405064`): функция перебирает записи текущего шага, ищет объект по имени записи, назначает ему MULT/номер шага/индекс объекта и затем увеличивает номер шага. Поэтому ранее осторожное обозначение «верхнеуровневые записи» здесь уточнено до кадров временной последовательности.

**HYPOTHESIS для `0x0004`:** число используемых записей палитры. Во всех 450 файлах, содержащих RLE, поле равно `max_used_palette_index + 1`; используемые индексы всегда меньше него. Но рассмотренный оригинальный декодер не использует это поле как длину цикла; указатели палитры и кадров задаются фиксированными смещениями. Не трактовать его как ширину, высоту, FPS, размер заголовка или адрес.

## 3. Общая запись объекта — CONFIRMED

Смещения относительно начала записи `R`:

| Смещение | Размер | Содержание |
|---|---:|---|
| `+0x00` | 50 | Область метаданных; начинается с NUL-терминированного имени объекта |
| `+0x32` | 4 | `int32 type` |
| `+0x36` | 4 | `uint32 record_size`, включая все поля и последние 8 байт |
| `+0x3A` | 4 | Ширина изображения или номер шага ссылки, по типу |
| `+0x3E` | 4 | Высота изображения или индекс объекта ссылки, по типу |
| `+0x42` | переменный | Данные конкретного типа |
| `+record_size-8` | 4 | `float32 x` |
| `+record_size-4` | 4 | `float32 y` |

**Неизвестно:** внутреннее разбиение первых 50 байт. Там встречаются дополнительные строки (`Mainhero`, `Walk0`, имена `.tzp`) и похожие на адреса значения. Нельзя объявлять их ссылками, указателями или самостоятельными полями без проверки. Для декодера достаточно сохранить все 50 байт как opaque metadata и извлечь первую строку для имени объекта. `FUN_00405064` передаёт начало записи в поиск объекта по имени — это доказывает использование первой строки, а не назначение остальных байт.

## 4. Тип -16 (`0xFFFFFFF0`): палитровое RLE — CONFIRMED

```text
+0x3A uint32 width
+0x3E uint32 height
+0x42 uint16 tokens[...]       // до последних 8 байт записи
end-8 float32 x
end-4 float32 y
```

Каждое 16-битное слово:

```text
bits  0..11: palette_index, 0..4095 в кодовом слове
bits 12..15: run_length_minus_1, 0..15
run_length = (token >> 12) + 1  // 1..16 пикселей
```

Однако фиксированная область файла содержит только **4094** записи палитры. Для независимого безопасного декодера индекс `>=4094` недопустим; в данном корпусе максимальный индекс — 3714. Нельзя читать за пределами палитры только потому, что кодовое слово технически вмещает 4096 значений.

Серии декодируются слева направо по строкам; каждая строка должна набрать ровно `width` пикселей. Нет маркера конца строки и нет перехода серии через её границу. После `height` строк поток заканчивается перед двумя координатами. Это не дельта-кадры и не LZ-поток: показанный оригинальный декодер пишет каждый пиксель выводимого прямоугольника непосредственно из палитры.

Доказательство — `FUN_00401d00` (`ev_2e89c9f154f9b701b39ddba69ff18557c7762ec1254543415896211db1d9d64c`):

```asm
0x401d2c ADD EBX, 0x8               ; palette = raw MULT + 8
0x401d37 LODSW ESI                  ; uint16 token
0x401d3b SHR ECX, 0xc
0x401d3e AND EAX, 0xfff
0x401d43 INC ECX                    ; run_length
0x401d44 SUB EBP, ECX               ; remaining pixels in row
0x401d46 MOV EAX, [EBX + EAX*4]      ; palette entry
0x401d49 STOSD.REP ES:EDI
0x401d4d JNZ 0x401d35               ; next run in this row
0x401d4f ADD EDI, [0x443148]         ; destination pitch correction
0x401d55 DEC [0x443140]             ; remaining rows
```

`FUN_004031f8` выбирает декодер по глубине цвета: 15-битный `0x4020f3`, 16-битный `0x401ec9`, 32-битный `0x401d00`; другие ветки добавляют смешивание. RLE-поток начинается на 16 байт дальше указателя на поле type, то есть `R+0x42`.

Найдены **172 нулевых растра**: ширина и/или высота равны нулю, поток пуст. Не создавать для них текстуру нулевого размера. Потребители `0x404974` и `0x40445c` проверяют ширину на ноль до рисования/проверки попадания.

## 5. Палитра и прозрачность

**CONFIRMED:** порядок байт записи палитры — **B, G, R, A**. 32-битный декодер копирует слово без перестановки; 16-битный `0x401ec9` извлекает красный из старших цветовых битов, зелёный из средних, синий из младших. `FUN_0040ef38` для 24/32 бит формирует `R<<16 | G<<8 | B`.

**CONFIRMED:** четвёртый байт влияет на смешивание. `FUN_00401d60` читает его, отдельно обрабатывает нулевое значение и значения `>=254`; для частичной прозрачности прибавляет к исходным цветовым компонентам вклад фона с коэффициентом, полученным из альфы. Инструкции: `0x401df8 SHLD EDX,EAX,8`, `0x401dfc CMP EDX,0`, `0x401e0e CMP EDX,0xfe`, `0x401e9f PSUBUSB`, `0x401eb9 PMULLW`, `0x401ebc PSRLW ...,8`, `0x401ec0 PADDUSW`.

**Не подменять это стандартным straight-alpha RGBA.** В исследованной ветке RGB не домножается на собственную альфу, как в обычном straight-alpha blend; отдельный параметр цветового воздействия/затухания также участвует в вычислениях. Но и объявлять все данные строгими premultiplied RGBA нельзя: среди используемых палитровых значений **1008** нарушают условие `RGB <= A`, превышение достигает 47. Принудительная нормализация или unpremultiply изменит оригинальные данные.

Для спецификации декодера правильный контракт — возвращать исходные BGRA и индексы без исправлений. Для точного вывода нужен отдельный совместимый compositor; перенос в стандартный PNG с альфой не гарантирует идентичность оригинальному смешиванию. Созданные PNG — непрозрачные иллюстративные композиции на шахматном фоне, не эталонные PNG исходной альфы.

**CONFIRMED:** оригинал также использует цвет `0xB5B5B5` для проверки прозрачных участков. `FUN_0040445c` декодирует изображение и сравнивает RGB пикселя с `FUN_0040ef38(0xB5,0xB5,0xB5)` при hit-test. `FUN_0040f5e8` вызывает `FUN_0040efa8` для двух поверхностей с этими же аргументами; helper вызывает виртуальный метод по `+0x74`. Это согласуется с установкой DirectDraw color key; идентификация виртуального метода как SetColorKey — интерпретация интерфейса, не символ из EXE.

**Нельзя считать индекс палитры 0 всегда прозрачным:** значение элемента 0 различается между файлами. В `walk0` по смещению `0x8` находится `B5 B5 B5 00`, но, например, `Start_m.MULT` начинает палитру с `42 42 3F DA`. Решение принимается по данным/режиму композиции, не по одному индексу.

## 6. Тип -13 (`0xFFFFFFF3`): ссылка на запись — CONFIRMED

Размер всех встреченных записей этого типа — **74 байта** (`0x4A`):

```text
+0x3A uint32 target_frame     // 1-based
+0x3E uint32 target_object    // 0-based в списке записей шага
+0x42 float32 x              // собственные координаты ссылки
+0x46 float32 y
```

Доказательство: `FUN_0040c14c`, `ev_3398fa375cc0ca34c384c3e32c6e7592fc2a3824883503f272da593d7c1634df`:

```c
record = frame_index[frame - 1] + 4;
for (i = 0; i < object; i++) record += read_u32(record + 0x36);
if (read_i32(record + 0x32) == -13)
    return resolve(mult, read_u32(record + 0x3a), read_u32(record + 0x3e));
```

Ссылки могут быть цепочками; независимый декодер должен проверять диапазоны и циклы. Все 11 355 ссылок корпуса прошли такую проверку.

**Важная семантика:** изображение и его метаданные разрешаются рекурсивно, а координаты берутся из исходной записи текущего шага. `FUN_0040c1f0` не вызывает resolver: проходит до конца выбранной исходной записи и возвращает `end-8`. Поэтому нельзя просто заменить запись-ссылку целевой записью целиком — потеряются координаты текущего шага.

Пример: `block10/Xsh/Scn_44/Step_05.MULT`, запись по `0x33D06`: type `-13`, size `74`, target frame `17`, target object `0`, координаты лежат по `0x33D48` и `0x33D4C`.

Размер всех встреченных записей — **330 байт** (`0x14A`):

```text
+0x3A uint32 width
+0x3E uint32 height
+0x42 char external_path[256]  // до первого NUL
+0x142 float32 x
+0x146 float32 y
```

Пример `block10/Xsh/Scn_41/Start.MULT`, запись `R=0x4004`:

- name: `Left_stolb`;

- size: `330` по `0x403A`;

Доказательство — `FUN_00404eb0`, `ev_8e3d66ff1d1193623252655c8fab416dcb474168c2fdc83dd2105d59a89a3aab`:

```c
image = get_image_header(mult, frame, object);  // R + 0x32
```

Изменение происходит только в загруженном буфере оригинального процесса: путь затирается указателем и тип меняется на **-12**. В исходных 505 MULT тип `-12` не встречается. Не считать `-12` дополнительным дисковым форматом на основании этой runtime-мутации.

Декодер должен использовать case-insensitive каталог ресурсов и нормализовать `\` в `/`, не исправляя исходные пути.

Проверены все 678 внешних ссылок:

- 677 находят файл; 676 совпадают по размерам с TIFF IFD.
- `block8/Xsh/Scn_35/Start.MULT`, кадр 1, объект 4: отсутствует `Tzu\Scn_35\Zanaves\S0\san.tif` в извлечённом наборе.
- `block5/Xsh/Scn_19/Start1.MULT`, запись по decimal `20678` (`0x50C6`): MULT задаёт **71×185**, найденный TIFF — **69×185**. Причина не установлена; размеры не следует молча «исправлять».

Для пикселей внешнего типа необходимо отдельно декодировать указанный TIFF. MULT не содержит этих пикселей. Полное побитовое воспроизведение TIFF-конвертера оригинала в эту работу не входит.

## 8. Координаты и привязка

**CONFIRMED:** последние 8 байт каждой записи — два `float32`, а не дополнительное RLE, счётчики или кадры. `FUN_0040c1f0` возвращает эти 8 байт; потребители `0x404974` и `0x40445c` используют инструкции `FLD/FCOMP` и копируют значения в поля положения объекта.

Если оба значения равны нулю, показанные потребители сохраняют прежнее положение. Если хотя бы одно ненулевое, записывают новые X/Y и устанавливают оба коэффициента масштаба в `1.0` (`0x3F800000`). Примеры инструкций: `0x404a06–0x404a40`.

В растровой области нет дополнительных подтверждённых полей anchor/pivot. При рисовании потребитель использует половины ширины/высоты; видны преобразования положения с половиной размеров области отображения и внешними смещениями: `0x404a46–0x404a8d`. Значения Y участвуют с противоположным знаком относительно X. **Полная семантика системы координат, камеры и перехода к сценовым координатам здесь не восстановлена.** Нельзя называть эти float непосредственно экранными координатами или координатами ног героя.

Например, у `walk0`, шаг 1: `(0,0)`; у `Start_m`, шаг 1: примерно `(-532.6801,69.0000)`; у `block8/Xsh/Scn_31/Step_02.MULT`, объект `Dog1`: примерно `(-197.5789,-55.4654)`.

```text
0x4036: F0 FF FF FF          type = -16
0x403A: 5C 2C 00 00          record_size = 11356
0x403E: 77 00 00 00          width = 119

0x4046: 00 F0 ...            RLE: index 0, length 16
```

Первый поток содержит 5641 слово RLE (`11282` байта), выдаёт `119×283=33677` пикселей. `50+16+11282+8=11356`. У `walk1` первый поток содержит 4490 слов; `50+16+8980+8=9054`.

Сводная проверка корпуса:

- 505 непустых файлов, **15920 временных шагов**;
- 27131 запись, только типы `-16`, `-13`, `-14`;
- точное окончание каждого файла, без непрочитанного хвоста;
- все 15098 RLE проверены по строкам и точному исчерпанию потока;
- все 11355 ссылок разрешены с проверкой циклов;
- 172 пустых растра корректно выделены отдельно;
- семь предварительных PNG; кадры `walk0`/`walk1` визуально просмотрены и показывают согласованные изображения героя в разных направлениях;
- все 506 файлов, включая пустой, побайтно совпадают с RSS.

Это структурная, алгоритмическая и визуальная проверка, **не дифференциальное сравнение с запущенной игрой**.

## 10. Минимальный контракт будущего декодера

1. Читать header и палитру с фиксированными смещениями; не вычислять их размер из неизвестного поля `0x4`.
2. Построить индекс шагов и записей последовательным проходом по `record_size`.
3. Сохранить исходные метаданные и координаты каждой записи.
4. Для `-16` декодировать RLE в индексы/неизменённые BGRA; отдельно обрабатывать нулевые размеры.
5. Для `-13` разрешать изображение рекурсивно, но брать позицию из исходной записи текущего шага.
6. Для `-14` возвращать внешний путь и оба набора размеров при несовпадении с TIFF; отсутствие ресурса — явная диагностика.
7. На неизвестных типах, недопустимых размерах, выходе индекса или цикле ссылки выдавать ошибку, не угадывать продолжение.

Скорость воспроизведения не найдена как отдельное поле в восстановленной структуре MULT. Есть внешний планировщик и SCC; числа `32`/`36` из `Animc` в `Mainhero.scc` **не равны** числу шагов `walk0`/`walk1` (оба 24). Их точное назначение не исследовано и не должно подменяться FPS по предположению.

## 11. Остаточные неизвестные

| Статус | Вопрос | Что нужно для закрытия |
|---|---|---|
| HYPOTHESIS | `u32@0x4` — размер используемой палитры | Найти его потребителя или экспортёр; наблюдаемая корреляция уже проверена на всех RLE-файлах |
| UNKNOWN | Схема остальных байт metadata[50] | Найти чтения отдельных смещений, если это потребуется; текущий декодер от них не зависит |
| UNKNOWN | Точная глобальная система координат | Проследить параметры камеры/области отображения и сверить с оригиналом |
| UNKNOWN | Полностью идентичное смешивание, затухание, масштабирование | Отдельно восстановить выбранную ветку renderer и провести дифференциальные проверки |
| UNKNOWN | Причина пустого MULT, пропавшего TIFF и расхождения 71/69 | Проверить использование сценариями и поведение оригинала; не менять данные |

**Итог:** бинарная структура и пиксельное кодирование восстановлены и проверены на всём доступном корпусе. Основные оставшиеся вопросы относятся к точному runtime-рендерингу, семантике метаданных и аномалиям исходных данных, а не к границам записей или алгоритму RLE.
