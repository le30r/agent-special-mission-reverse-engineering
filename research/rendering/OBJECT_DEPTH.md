# Agent.exe: глубина сценовых объектов (`Object`)

Дата: 2026-10-18. Объект анализа — оригинальный PE32/x86 `agent-original/game-installed/Program_Executable_Files/Agent.exe`, SHA-256 `71065c571a9cd40f460458d766720c0a01954e0bef521aad675b4ea6b3186e85`, image base `0x400000`. Адреса ниже — VA. Ghidra 12.1.4 через REA. Доказательства: [`evidence/rea-object-depth.json`](evidence/rea-object-depth.json) (выгрузка REA/Ghidra с инструкциями, псевдокодом и evidence ID) и [`evidence/offset-references.txt`](evidence/offset-references.txt) (независимая выборка `objdump` по смещениям). Оригинальный Windows-процесс не запускался: `CONFIRMED` означает статическое доказательство машинным кодом и/или исходным SCC, не runtime-наблюдение.

Использованы ранее установленные факты из [NAVIGATION_SCALE](../navigation/NAVIGATION_SCALE.md), [SCC_RUNTIME](../scc/SCC_RUNTIME.md), [MULT_FORMAT](../mult/MULT_FORMAT.md). Повторного исследования этих подсистем и правок браузерного движка нет.

## Итог — CONFIRMED

```text
Object <name> <cursor_id:int32> <depth:int32>
                  │                │
                  └─ object+0x152  └─ object+0x108
```

`+0x108` — **знаковое 32-битное поле**, начальное значение которого дословно равно **второму числу** после имени. Это не `State` (`+4`), не индекс MULT, не первый аргумент `Object`, не вычисление из координаты Y. `+0x152` — ID курсора при наведении на объект. Для обычного `Object` других числовых аргументов нет. Тип базового объекта задаётся vtable `0x443e54`, а не первым числом. Пример: `Object Lect 5 14` → `+0x152=5`, `+0x108=14`, `+4=0` при создании.

### Парсер и конструктор

1. `0x4058d8` хеширует токен SCC. `Object` даёт `0x16040`; dispatch в `0x4068b3–0x4068ba` ведёт к `0x406b7a`. `Active` даёт `0x12a60` и ведёт к `0x406adf`. `Objzet` даёт `0x16057` и ведёт к `0x407653`. Хеш подтверждается алгоритмом `1000,100,10,1,1,1` в `0x4058d8` и исходными токенами SCC.
2. `0x406b7a–0x406b94`: `sscanf`-подобному `0x438e6c` передаются строка, формат по `0x444b18` (`%s %d %d`), адреса локальных `name`, `first` (`[EBP-0x5c]`), `second` (`[EBP-0x60]`). Если `Scene+4 != 0`, ветка пропускает создание (`0x406b97–0x406b9c`). Результат парсинга не проверяется по числу совпавших полей; поведение некорректной строки остаётся UNKNOWN.
3. `0x406ba2–0x406bd2`: выделяется `0x287` байт, конструктору `0x404150` передаются `self`, `name`, **first**, **second** (последовательность `PUSH` от `0x406bba` до `0x406bcd`; cdecl кладёт последний аргумент первым). Затем `0x406be3–0x406c18` сравнивает имя с `Mainhero` и, при совпадении, пишет указатель в `Scene+0x76e`; `0x406c1e–0x406c2b` добавляет объект в сцену через `0x405c10`.
4. `0x404150`: `0x404168 MOV [EBX],0x443e54`; `0x40416e MOV [EBX+4],0`; `0x404173 MOV ECX,[EBP+0x14]` / `0x404176 MOV [EBX+0x108],ECX` — **second**; `0x404194 MOV EDX,[EBP+0x10]` / `0x40419a MOV [EBX+0x152],EDX` — **first**; `0x4041a2` берёт `name` из `[EBP+0xc]` и копирует в `+8`.
5. `0x405c10` при повторном имени заменяет объект и переносит только прежний `+4` (`0x405c30–0x405c4e`). Глубина и cursor ID нового экземпляра не наследуются; остаются значениями нового объявления. Существование дубликата в конкретной сцене отдельно не утверждается.

`Active` — **самостоятельный объект**, не настройка глубины объекта с похожим именем. Его ветка `0x406adf–0x406b55` читает имя, два числа и четыре координаты; `0x404bf0` передаёт первые два числа в тот же `0x404150` (`0x404c09–0x404c1b`), после чего меняет vtable на `0x443e20` и сохраняет прямоугольник. Например, `Active Goto_5 3 230 1350 180 1450 280` даёт `Goto_5.+0x152=3`, `Goto_5.+0x108=230`; на `Lect` это не влияет.

### Все обнаруженные пути записи глубины объекта

| Адрес | Условие и источник | Эффект |
|---|---|---|
| `0x404176` | `0x404150` при создании `Object`, `Active` и иных подклассов | `+0x108 =` последний аргумент конструктора; для SCC `Object` это второе число |
| `0x405227` | `0x405064`, звуковое/кадровое событие: `record+4 == -1` и текущий кадр `anim+0x311 == record+0`; имя `record+0xc` ищется через `0x40a8dc`, строка `record+0x50c` переводится в int через `0x43d1ec` | `named_object.+0x108 = parsed_int` |
| `0x406454` | SCC executor `0x405e5c`, opcode `0x13` (`Objzet name value`) | непосредственная запись `value` в найденный объект; код не проверяет нулевой результат поиска |
| `0x4064e4`, `0x4064fd` | SCC opcode `4`: при `value>0` сохранить `abs(hero.depth)` в глобальный `0x468118` и назначить `hero.depth=value`; при `value<=0` восстановить глобальное значение | временная ручная глубина только героя; имя этой команды в исходном корпусе не установлено |
| `0x40871c`, `0x40977c` | вход в сцену и обычный `Setxy`/перемещение героя; вызов `0x405968` | герой получает глубину из маски, перезаписывая объявленное `Object Mainhero 0 10` |
| `0x404339` → `0x439004` | загрузка сериализованного состояния объекта | `+0x108` восстанавливается из сохранения; `0x40424d` → `0x438e28` записывает его при сохранении |

Инвентаризация `objdump` также находит `0x40348a MOV [EDX+0x108],ECX`, но это **другая структура**: `0x4033c8` заполняет ресурс фона, а `0x405a9b–0x405aa9` читает его `+0x104/+0x108` как ширину/высоту. Не смешивать одноимённые смещения разных типов. `LEA [object+0x108]` в `0x40424d/0x404339` учтены как save/load, хотя это не прямые `MOV`-записи.

`Fram` с `end=-1` — именно переключение глубины, **не изменение `State`**. В `Level1.scc:91` есть `Fram 3 -1 1 Y_lec_r 14`; это меняет `Y_lec_r`, не `Lect`. Другой пример: `Level14.scc:45–46` задаёт `Pocruv` последовательно `165` и `160`. `Anim`, `Animc`, `Start`, `StartW` сами по себе не передают новое значение глубины; они могут запустить `0x405064`, который выполнит такой `Fram`. Кадровые записи с `end=0` или положительным `end` идут по веткам звука и не выполняют запись `0x405227`.

`State name value` идёт через `0x405b78` и пишет `object+4`, не `+0x108`; `Cursor name value` (opcode `0x1f`) пишет `+0x152` (`0x406593`), не глубину. Пример `Level1.scc:251–252`: `Cursor Lec_v 2`, `Cursor Slip 5`. `Objzet` — отдельная явная команда изменения глубины: `Level5.scc:175–181` переключает `Col_all` между `5` и `1010`, `Col_vaz` между `6` и `1000`. `Active` только создаёт свой объект.

### Чтения, знак и порядок

`0x40a4ac` читает два `+0x108` (`0x40a4b5`, `0x40a4c8`), делает двоичный `abs` через `CDQ; XOR; SUB` и возвращает `abs(rhs)-abs(lhs)` (`0x40a4d7`). `0x40a4dc` передаёт его сортировщику `0x44061c`; следовательно, **по модулю убывает сортировочный ключ**: большие `|depth|` оказываются раньше в массиве. `0x40a76c:0x40a7f0–0x40a7f6` вызывает сортировку после обновления SCC, анимаций и движения и до прохода по объектам. При обычном painter order меньший модуль накладывается позже. Порядок объектов с равными ключами компаратор не определяет; стабильность сортировки не доказана.

Знак **не кодирует отдельную сторону слоя в компараторе**: `+14` и `-14` имеют равный ключ. Hit-test `0x40a2bf–0x40a2ce` и другие проверки попадания `0x40a003`, `0x40a421` требуют `abs(depth)>0` после pixel/rect hit-test. Но знак **нельзя объявлять глобально несущественным**: `0x404974:0x404980–0x40498b` сравнивает исходное знаковое значение с `10000` и при `>=10000` обходит обновление изображения; `0x40402c:0x4040c6–0x404103` использует исходные знаковые разности глубин в отдельном расчёте. Из одного компаратора нельзя выводить, что отрицательная глубина идентична положительной во всех подсистемах. Для `INT_MIN` последовательность `CDQ; XOR; SUB` оставляет `0x80000000` из-за 32-битного переполнения; обычное математическое `abs` имеет эту границу.

## Первая сцена и Lect — CONFIRMED

Исходный `Scripts/Level1.scc:17–18`:

```text
Object Lec_v 0 100000
Object Lect 5 14
```

Сразу после парсинга `Lect.depth=14`, `Lect.cursor_id=5`, `Lect.State=0`; `Lec_v.depth=100000` — **другой объект**. `Level1.scc:175` использует `Lect` в `Click`, но `Click` не назначает глубину. В `Level1.scc` нет `Objzet Lect`, `Cursor Lect` или `Fram … -1 … Lect …`; следовательно, в исследованном SCC для `Lect` нет явного последующего изменения глубины. В `Level37.scc:14` этот же объект объявлен как `Object Lect 5 14`. Высокие значения вроде `100000` имеют особый путь обработки изображения при `>=10000` (`0x404986`); называть их просто «очень дальним декором» неверно.

Герой в этой сцене объявлен `Object Mainhero 0 10` (`Level1.scc:5`), но после размещения его `+0x108` пересчитывается из `Mask` и `Focus` (`0x40871c`, `0x40977c`), в отличие от статического `Lect`. Уже установленный пример из NAVIGATION_SCALE: в `(660,480)` герой имеет `z=14`; в `(250,480)` — `z=13`. Это сравнение сортировочных ключей, **не доказательство конкретного пиксельного перекрытия `Lect` героем**.

## Оставшиеся HYPOTHESIS / UNKNOWN

- **HYPOTHESIS:** положительная глубина сцены — авторская координата «дальше/ближе» относительно маски героя; корпус `Object` (566 объявлений в оригинальных SCC) не содержит отрицательных вторых чисел, поэтому физическое направление оси Z по знаку не установлено. Подтверждён только порядок наложения по модулю.
- **UNKNOWN:** точный видимый эффект отрицательной глубины в остальных ветках рендера и значение `INT_MIN` в реальном запуске. Нет исходного SCC-примера `Object` с отрицательной глубиной.
- **UNKNOWN:** точное поведение malformed `Object`, отсутствующего имени в `Objzet`/`Fram`, равных sort keys и возможной десериализации сохранённой глубины `Lect` в конкретной игровой сессии. Статический код не следует выдавать за трассу исполнения Windows-процесса.

Аргументы корректно сформированных `Object` и `Active` не относятся к этим гипотезам: подтверждено, что первое число — cursor ID (`+0x152`), второе — depth (`+0x108`). `Active` при этом остаётся отдельным видом объекта.
