# SCC runtime: полный путь подбора бутылки

Дата: 18 октября 2026. Basic Memory: проект `agent-reverse`.

## 1. Результат и границы доказательств

Восстановлена статическая модель `Click 0 Botl Botl` из `Scripts/Level1.scc`: регистрация обработчика, выбор по предмету и состоянию, запуск списка команд, ожидание пути, ожидание анимации, установка координат, запись в инвентарь и изменение состояния. Исполнение — **кооперативные возобновляемые списки команд, опрашиваемые игровым тиком**, а не выполнение всего блока за один вызов и не обнаруженная FIFO-очередь SCC-событий.

**CONFIRMED (static)** далее означает непосредственно установленное устройство исследованного бинарника или содержимое оригинальных ресурсов. Это **не подтверждение наблюдаемого поведения запущенной игры**. Оригинал не запускался, динамического trace нет. Последовательность полного успешного взаимодействия ниже — вывод из связанного control/data flow при явно заданных условиях. **HYPOTHESIS** — интерпретация, для которой цепочка неполна; **UNKNOWN** — оставшийся вопрос. Имена `Scene`, `Handler`, `Program`, `busy`, `pc` ниже введены исследователем, не извлечены из символов EXE. Нормализованный C-подобный код — пересказ Ghidra, не исходники игры.

## 2. Источники и адресный маршрут

Начальная зацепка: строка `Start` по `0x444b80` → xref `0x40816e` в загрузчике сцены `0x407ffc` → загрузка SCC `0x4066c8` и диспетчер событий `0x4079ac`. Строки `click` по `0x40ad00`/`0x40ae30` не дали xrefs и не использованы как доказательство парсера. Из парсера адресно исследованы конструкторы обработчика/списка, исполнитель, его вызывающие функции, движение, анимация и инвентарь. Полная декомпиляция движка не выполнялась.

Локальные доказательства, включая Evidence ID, SHA-256, профиль и ограничения REA:

- `evidence/0x4066c8.json` — dossier парсера: декомпиляция, инструкции, ссылки, CFG;
- `evidence/0x405e5c.json` — dossier исполнителя и таблица dispatch;
- `evidence/0x40a238.json` — dossier обработки клика по сцене;
- `evidence/pseudocode.json`, `evidence/supplemental.json` — остальные адресно выбранные функции;
- `evidence/assembly.json` — инструкции ключевых функций;
- `evidence/data.json` — байты scanf-форматов и vtable объекта;
- `evidence/source_facts.json` — SHA-256 EXE, всех 57 SCC и двух MULT; исходный блок с номерами строк и хеши команд;
- `evidence/bottle_mult.json` — все кадры двух относящихся к бутылке MULT, имена, смещения, размеры и позиции.

Ключи `pseudocode.json` иногда являются адресом внутри функции: канонический entry указан в тексте Ghidra. Например, селектор `0x408d40` возвращает `FUN_00408d24`, `0x40a786` — `FUN_0040a76c`, `0x409dff` — `FUN_004099c0`, `0x40f329` — `FUN_0040f204`. Это не разные функции.

## 3. Как SCC превращается в исполняемые списки

### 3.1. Лексическая диспетчеризация — CONFIRMED (static)

`FUN_004066c8` читает токены через `FUN_00438e6c` с форматом `%s` (`0x444aeb`), вычисляет хеш `FUN_004058d8` и выбирает ветку по числу. Поэтому большинство ключевых слов не присутствует в EXE отдельными строками.

`0x4058d8`, нормализованный фрагмент:

```c
if (strlen(token) >= 7) return 0;
weight = 1000;
for (byte c : token) {
    hash += c * weight;
    if (weight > 1) weight /= 10;
}
```

Это слабый регистрозависимый хеш, без доказанной последующей проверки полного имени. Нельзя называть его полноценной таблицей точного сравнения строк. Неизвестные токены, включая отдельную `{`, не порождают инструкцию в рассмотренной ветке; `}` имеет собственную ветку освобождения текущего незарегистрированного списка. Грамматика читается токенами, а не строго по строкам.

| SCC | Хеш | Действие при загрузке | Runtime opcode |
|---|---|---|---|
| `Click` | `0x134d0` | создать Handler | нет |
| `Case` | `0x1307f` | привязать текущий Program к индексу состояния | нет |
| `Break` | `0x13316` | начать новый пустой Program | нет |
| `Goto x y` | `0x145ab` | записать два int | `2` |
| `StartW name` | `0x1768f` | записать имя анимации | `1` |
| `Start name` | `0x17638` | записать имя анимации | `0` |
| `Setxy x y` | `0x17125` | записать два int | `6` |
| `Addtol id` | `0x12a2f` | записать ID предмета | `0x0f` |
| `State name value` | `0x1762b` | записать имя и int | `3` |

Адресные фрагменты `0x4066c8`: `Click` — `0x407155–0x40725e`; `Case` — `0x407266–0x407293`; `Break` — `0x407298–0x4072cb`; `State` — `0x4072e9–0x40731a`; `StartW` — `0x4073a3–0x4073ce`; `Start` — `0x4073d3–0x4073fe`; `Goto` — `0x407523–0x407551`. Остальные ветки сохранены в полном адресном dossier.

### 3.2. Click и Case — CONFIRMED (static)

Форма:

```text
Click <itemId:int> <eventName:string> <stateObject:string> [stateScene:int]
```

Парсер сначала читает `%d %s %s` по `0x407167`, затем ещё токен: если это `{`, сцена состояния равна `-1` (текущая); иначе токен преобразуется в номер сцены. Если вместо `stateObject` прочитана `{`, используется `Interface`, сцена `-1`. Это наблюдаемые особенности оригинального загрузчика, не рекомендация менять исходный SCC.

`FUN_00408a48` создаёт Handler размером `0x2d4`:

| Смещение байт | Значение |
|---|---|
| `+0x000` | сцена объекта состояния, `-1` означает текущую |
| `+0x004` | имя события, например `Botl` |
| `+0x104` | имя объекта, чьё состояние проверять, например `Botl` или `Flag1` |
| `+0x208` | 50 указателей `Program`, индексы состояния `0..49` |
| `+0x2d0` | требуемый ID выбранного предмета |

Scene содержит число обработчиков по `+0x56d`, указатели — с `+0x571`. Запись: `0x40721b MOV EDX,[ESI+0x56d]`, `0x407221 INC [ESI+0x56d]`, `0x407227 MOV [ESI+EDX*4+0x571],EAX`.

`FUN_00408c74`, вызываемый из ветки `Case n`:

```c
*(Program **)(handler + 0x208 + n * 4) = currentProgram;
```

`Break` **не является исполняемым выходом из switch**. Он выделяет новый пустой список `0x29eb` байт через `0x405c6c`; следующий `Case` будет связан уже с ним. Поэтому соседние `Case 1; Case 3; ... Break` ссылаются на один список. Это не последовательные runtime-проверки с fall-through. При закрывающей `}` освобождается текущий после `Break` пустой список; привязанный предыдущий список сохраняется. Отсутствие `Break` перед `}` нельзя автоматически считать безопасным: оригинальная ветка освобождает текущий указатель.

`FUN_00405cac` добавляет команду в Program. Размер записи `0x10c` байт: opcode `+0`, int A `+4`, int B `+8`, строка `+0x0c` (256 байт). В начале Program — число команд `u32`, затем записи с `+4`. В блоке бутылки ровно пять команд: `2,1,6,15,3`. Ограничение конструкции — 40 записей до служебных байт; проверки переполнения в рассмотренном append отсутствуют. Совместимому безопасному интерпретатору не следует воспроизводить повреждение памяти оригинала.

## 4. Цепочка от мыши до первого Goto

**CONFIRMED (static), обычный путь при отсутствии модального видео/UI и busy:**

```text
0x40f204  window procedure, message 0x201 (WM_LBUTTONDOWN)
  → 0x40cb84  UI-mode dispatch, mode 0
    → 0x40a238  scene click/hit-test
      → 0x4079ac  dispatch by eventName, selectedItemId
        → 0x408cd8  check itemId + state-selected Program
          → 0x405d30  activate/reset Program
            → 0x405e5c  execute immediately until yield/end
```

В `0x40f204` координаты извлекаются из младших/старших 16 бит lParam. В `0x40a238` к X прибавляется горизонтальный offset Scene `+0x766`. Объекты просматриваются с конца отсортированного массива `Scene+0x335`, вызывается virtual hit-test `vtable+8`, затем проверяется ненулевое абсолютное значение поля объекта `+0x108` (не `State`). Для `Object Botl 6 1000` это отдельные параметры, не начальное состояние 6 или 1000.

Для базового `Object` vtable `0x443e54`, слот `+8` содержит `0x40445c`: проверка прямоугольника и пикселя изображения, включая color key. Это согласуется с предыдущим исследованием MULT; не достаточно одного прямоугольника. `State` в hit-test напрямую не сравнивается.

После попадания вызывается, нормализованно:

```c
dispatch(scene, /*executionMode=*/0, *(int *)(scene+5), objectName);
```

`Scene+5` — выбранный предмет: `0x40a194` пишет туда ID, переданный при выходе из инвентаря `0x40e9f0`; ноль — обычное взаимодействие без предмета. `0x40ed08` получает ID из массива инвентаря по позиции UI. Следовательно, `Click 1 Slip Flag1` означает событие на `Slip` при выбранном предмете 1 с выбором ветки по `Flag1`, а не второй тип кнопки мыши.

`0x4079ac` перебирает **все** Handler сцены, сравнивает имя события и OR-ит результаты. Он не останавливается на первом совпадении. `0x408cd8`:

```c
state = readState(handler, scene);             // 0x408c8c
if (handler.itemId == selectedItemId && handler.program[state] != NULL) {
    activateAndRun(handler.program[state], executionMode, scene);
    return true;
}
return false;
```

`0x408c8c` ищет `handler.stateObject` через `0x40a8dc`, в текущей сцене либо через таблицу `0x46851c[stateScene]`, возвращает `object+4`; если объект не найден, возвращает 0. `0x40a8dc` линейно перебирает список объектов и сравнивает имена через `0x435404`; последний сопоставляет символы через таблицу uppercase (`0x43c8a4`), поэтому поиск имён SCC-объектов регистронезависим и возвращает первое совпадение в порядке списка. Это относится и к привязке имён записей MULT в `0x405064` → `0x40a8dc`. Имя события в `0x4079ac` сравнивается напрямую побайтно — регистронезависимость объекта не распространяется на event name.

У `Botl` конструктор `0x404150` устанавливает `object+4=0`; при сохранённом прогрессе значение может быть восстановлено другим. Для свежего состояния 0 и выбранного предмета 0 выбирается Program из `Case 0`. Если уже `State Botl 1`, у этого обработчика нет Program[1], повторный подбор не запускается. Это не доказательство автоматического удаления объекта из сцены.

Перед новым обычным взаимодействием `0x40a238` вызывает `0x40a1bc(scene,0)` → `0x408d58`: у всех Program очищается active. Во время `Scene+0x709!=0` обычная обработка попаданий не выполняется; вместо неё вызывается `0x404ff4` для анимаций (попытка прерывания подходящего кадрового звука). Поэтому клик во время ожидания пути может заменить сценарий, а во время `StartW` идёт по другой ветке. Это не очередь «доиграть все клики».

## 5. Модель исполнения и планировщик

### 5.1. Контекст Program — CONFIRMED (static)

| Смещение байт | Смысл |
|---|---|
| `+0x0000` | число команд |
| `+0x0004` | начало массива записей размером `0x10c` |
| `+0x29e4` | active |
| `+0x29e5` | повторный вход в ожидающую команду (`waiting`) |
| `+0x29e6` | режим исполнения, переданный событием |
| `+0x29e7` | сохранённый индекс команды `pc` |

`0x405d30` записывает mode, active=1, waiting=0, pc=0 и **сразу** вызывает `0x405e5c`. Executor идёт по записям последовательно, пока команда не вернёт управление. На обычном продвижении `0x4065c8 INC EDI`, `0x4065c9 ADD EBX,0x10c`; в конце `0x4065d9 MOV [ESI+0x29e4],0`, `0x4065e0 MOV [ESI+0x29e6],0`.

Внешний UI update `0x40c974` вызывает тик сцены `0x40a76c`. Его порядок:

1. Перебрать Handler и все 50 непустых слотов Program: `0x40a786 → 0x408d24 → 0x405e5c`. Executor сам проверяет active.
2. Обновить активные анимации: `0x40a7b5 → 0x405064`.
3. Продвинуть движение: `0x40a7cd → 0x4099c0`.
4. Остальное обновление объектов/камеры/вывода.

Следствие: снятый при анимационном или навигационном update флаг обычно замечается списком на **следующем тике**, не callback-ом в том же месте. В бутылочном Handler только один слот Program[0], поэтому нет повторного обхода его через алиасы Case. Для нескольких Case, ссылающихся на один Program, оригинальный цикл обходит один указатель несколько раз — не следует бездумно заменять его уникальным Set активных задач при требовании точного порядка.

Между разными активными списками возможен кооперативный интерливинг по порядку Handler и Case. Доказательства отдельного потока на SCC-команду или общей FIFO-очереди событий в этой цепочке **нет**. Первичный dispatch синхронный; незавершённые списки живут в собственном контексте. На каждом тике они продолжаются независимо от нового чтения `State`: ветка выбирается при событии, а не заново при каждом resume.

### 5.2. Goto — CONFIRMED (static), обычный mode=0

Ветка opcode 2 по `0x405ff9–0x4060f1`:

```c
if (!waiting) {
    bool havePath = startPath(scene,x,y);      // 0x409964
    if (havePath) pc = currentCommand;
    // Дополнительная специальная проверка двух команд вперёд на StartW Speak.
    waiting = 1;
    return;
}
if (*(int *)(scene+0x72e) > 0) return;
waiting = 0;
// Продолжить следующей командой.
```

Ветка `Speak` проверяет opcode/имя **через две** записи (`[EBX+0x218]`, строка `Program+index*0x10c+0x228`), а не непосредственно следующую команду; для бутылки она не срабатывает. Нельзя обобщать этот код до «при отсутствии пути всегда пропустить анимацию».

`0x409964` обнуляет `Scene+0x72e/+0x732`, корректирует/проверяет цель через `0x409874`, строит путь через `0x408dc4` и возвращает `Scene+0x72e!=0`. `0x408dc4` хранит точки пути в глобальном массиве от `0x46179c`; у него есть своя кольцевая очередь поиска пути — **это не очередь SCC-событий**.

`0x4099c0` продвигает путь по времени и при окончании очищает оба поля:

```asm
0x409bd4 SUB [EBX+0x732],EAX
0x409be2 JG  0x409c88
0x409bec MOV [EBX+0x732],ECX  ; ECX=0
0x409bf2 MOV [EBX+0x72e],EAX  ; EAX=0
```

Executor ждёт `+0x72e`, не координатного равенства и не окончания Walk MULT. После очистки пути следующий тик снимает waiting и доходит до `StartW`.

Особые ветки, которые нельзя потерять:

- Режим исполнения 1 при `busy==0` вызывает `0x409708` немедленно и очищает путь; это **не** всегда блокирующий Goto. `0x40a3d8` отправляет mode=1 для отдельного пути ввода. `Click`-itemId и executionMode — разные аргументы.
- Если путь не создан, обычная ветка всё равно ставит waiting и делает yield. Сохранение pc в этой ветке условно: `0x406084 JZ 0x40608e`, запись pc только по `0x406086`. У бутылки Goto первый, сохранённый pc уже 0, поэтому следующий опрос может пройти дальше при нулевом `+0x72e`. Это не доказательство успешного прихода в точку; для Goto в середине другого списка возможен повтор от ранее сохранённого pc.
- Сам Goto не выставляет `Scene+0x709`; не следует считать его таким же input-lock, как StartW.

Точный алгоритм коррекции недоступной цели и численная навигация не специфицированы здесь: Ghidra в `0x409874`/FPU-ветках теряет часть register flow и выдаёт подозрительные выражения. Контракт ожидания доказан прямыми load/store/branch; точные координаты успешного оригинального пути динамически не проверены.

### 5.3. Start и StartW — CONFIRMED (static)

`Start` (opcode 0, `0x4061a0–0x4061d0`) находит анимацию через `0x40a980`, вызывает `0x404fb4(anim,1)` и сразу продолжает список. Анимация затем обновляется внешним тиком.

`StartW` (opcode 1, `0x405f7c–0x405ff4`):

```c
anim = findAnimation(scene,name);
if (!waiting) {
    waiting = 1;
    scene.busy = 1;                           // Scene+0x709
    startAnimation(anim,1);                   // 0x404fb4
    pc = currentCommand;
    return;
}
if (anim.active) return;                      // anim+0xbb9
scene.busy = 0;
waiting = 0;
// Продолжить следующей командой.
```

Ключевые инструкции: `0x405fab MOV CL,[EDX+0xbb9]`, `0x405fb3 JNZ 0x4065e7` (yield); `0x405fd9 MOV [EDX+0x709],1`; `0x405fee MOV [ESI+0x29e7],EDI`.

`0x404fb4` сбрасывает таймер `+0x20d`, ставит текущий кадр `+0x311=1`, сбрасывает ожидающий кадровый event `+0xbb1` и пишет active `+0xbb9`. Это не синхронное проигрывание MULT внутри StartW.

`0x405064` проверяет время, обрабатывает кадровые события, назначает изображения именованным объектам и увеличивает номер кадра. Для незацикленной анимации (`anim+0x200==0`), когда кадр превышает число кадров и нет блокирующего кадрового event, выполняет `0x4054ca CALL 0x404fb4` с аргументом 0. Тем самым снимается флаг, который опрашивает StartW. Зацикленная Animc возвращается к кадру 1 и сама таким путём не завершает ожидание.

Есть и отдельный механизм события по завершении: если `anim+0x211` — непустое имя, `0x4054eb → 0x4079ac` отправляет его как событие. Имя туда записывает `0x404e40`. Это не механизм resume StartW: бутылка возобновляется опросом active, не этим именованным событием.

**Уточнение тайминга предыдущей MULT-работы:** `0x404d90` рассчитывает период целочисленно `1000 / animationRate` и хранит по `+0x209`:

```asm
0x404de8 MOV EAX,0x3e8
0x404df4 CDQ
0x404df5 IDIV [EBP+0x10]
0x404dfd MOV [ECX+0x209],EAX
```

Для `Anim 12 Takedr1` получается 83 единицы внешнего tick-time на продвижение. Интерпретация как миллисекунд/FPS согласуется с формулой, но источник часов/реальный wall-clock и паузы не измерены. 52 кадра нельзя превращать в гарантированную длительность `52/12` секунды.

`Sound Takedr1` содержит `Fram 1 1 ...004.wav` и `Fram 32 0 ...002.wav`. В `0x405064` диапазон с ненулевым конечным кадром удерживает/возвращает кадровый cursor, пока проверка `0x402f18` не сигнализирует окончание; старт звука — `0x403d1c`. Поэтому звук может продлить ожидание всей анимации. Для `endFrame=0` есть отдельная неблокирующая ветка. Полный контракт аудио и поведение при отсутствующем/прерванном звуке не восстановлены; их нельзя заменить жёстким animation timeout.

## 6. Setxy, Addtol и State

### 6.1. Setxy — CONFIRMED (static)

Opcode 6, `0x40629b–0x406334`. Для положительных координат: запустить `Stop6`, применить его кадр через `0x405064(...,-1)`, очистить текущий image-cache героя `0x404414`, вызвать `0x409708(scene,x,y,1)`. Helper записывает логическую позицию `Scene+0x716/+0x71a`, проверяет/корректирует её, пересчитывает scale и координаты объекта героя, запускает/останавливает нужную stop-анимацию. Yield в этой ветке нет.

Для отрицательного X Setxy только сохраняет два int в логическую позицию. Есть глобальная ветка `0x444691`, позволяющая пропустить Setxy после специального Goto/Speak; в обычном бутылочном пути она не устанавливается. Следовательно, Setxy — не просто присваивание экранных координат sprite.x/y, но и не самостоятельное ожидание перемещения. Точные FPU-преобразования координат здесь не объявлены полностью восстановленными.

### 6.2. Addtol — CONFIRMED (static)

Диспетчер:

```asm
0x40640e MOV EDX,[EBX+4]       ; id
0x406411 PUSH EDX
0x406412 CALL 0x40c4c4
```

`0x40c4c4` вызывает `0x40ec2c(DAT_00468518,id)`. Реальная запись:

```c
for (int i=0; i<100; i++) {
    if (inventory.slot[i] < 0) {
        inventory.slot[i] = id;
        return;
    }
}
```

Физически слоты лежат с `inventory+4`, по 4 байта каждый; helper начинает с увеличения указателя. Внутри **нет** проверки дубликата, yield, назначения State или проверки «предмет уже изображён в руке». При полном массиве helper молча возвращается, после чего SCC всё равно может выполнить State. Для утверждения «предмет добавлен» требуется свободный слот.

`0x40ed88` рисует непустые слоты, обращаясь к `XSH\Interface\large.mult` с ID как номером кадра; `0x40ed08` возвращает ID при выборе позиции. Поэтому семантика массива как инвентаря установлена по потребителям, а не только по имени Addtol.

### 6.3. State — CONFIRMED (static)

Opcode 3, `0x406339–0x40635c` → `0x405b78(scene,name,value)`:

```c
object = findObject(scene,name);               // 0x40a8dc
if (object != NULL) *(int *)(object+4) = value;
else if (scene.loadFlag == 0) {
    object = newObject(name,0,0);              // 0x404150
    object.state = value;
    scene.objects.append(object);
}
```

Проверка отсутствующего объекта зависит от `Scene+4`. На уже найденном Botl запись непосредственная, без callback/очереди. Состояние — int по `object+4`; имя начинается с `+8`. Не путать с `object+0x108` (поле участия/видимости), кадром `+0x267`, индексом записи `+0x26b`, image-указателем `+0x14e` или координатами.

`0x40422c` записывает `object+4` в файл, `0x404318` читает его обратно; это доказывает включение State в сериализуемые поля объекта, **не** полную спецификацию save/load и повторного входа на уровень. `Lstate` (вне основного набора задачи) в executor opcode 10 вызывает тот же setter для другой Scene — состояния хранятся у объектов сцен, а не в одной глобальной переменной последнего Case.

## 7. Полное взаимодействие с бутылкой

Исходный блок `Scripts/Level1.scc`, строки 228–237:

```text
Click 0 Botl Botl
{
  Case 0
   Goto 660 480
   StartW Takedr1
   Setxy 670 477
   Addtol 1
   State Botl 1
  Break
}
```

Условия реконструкции успешного пути: сцена загружена, Botl.state=0, выбранный предмет=0, hit-test попал в Botl, путь построен и завершён, ресурсы/звук доступны, список не отменён новым взаимодействием, Takedr1 не зациклена и завершилась, в инвентаре есть свободный слот. Это **условный статический trace**, не запись с работающей игры.

| Этап | Program и условия | Изменения |
|---|---|---|
| До клика | inactive | Botl.state=0; предмет 1 ещё не добавлен этим блоком |
| Dispatch | Case[0], active=1, waiting=0, pc=0 | немедленный вход в Goto |
| Goto первый вход | pc=0, waiting=1, yield | создаётся путь к `(660,480)`; busy самим Goto не установлен |
| Тики движения | Program ждёт `Scene+0x72e>0` | Walk/координаты продвигаются внешним update |
| Путь завершён | navigation очищает `+0x72e/+0x732` | следующий тик снимает ожидание Goto |
| StartW первый вход | pc=1, waiting=1, busy=1, yield | Takedr1 active=1, cursor=1 |
| Анимация | Program ждёт `Takedr1+0xbb9` | внешний update меняет кадры и кадровый звук |
| Кадр 10 | ожидание StartW продолжается | Botl получает пустую MULT-запись; State ещё 0; Addtol ещё не вызван |
| Последний кадр/окончание | анимация снимает active | Program заметит это при последующем опросе |
| Resume StartW | waiting=0, busy=0 | сразу идёт дальше в том же вызове executor |
| Setxy | opcode 6 | установить/пересчитать позицию `(670,477)` |
| Addtol | opcode 15 | записать ID 1 в первый отрицательный слот |
| State | opcode 3 | Botl.state=1 |
| Конец списка | active=0, mode=0 | обработчик больше не имеет подходящей Case для state=1 |

Сохранённый pc не обязан обновляться на каждой неблокирующей команде и может остаться 1 после конца; окончание задаётся active=0, не `pc==length`.

### Различие визуального и логического подбора — CONFIRMED (static)

В `block9/Xsh/Scn_37/start.MULT`, кадр 1, запись Botl по файловому смещению `0x692e`: внешнее изображение **31×52**. `Step_02.MULT`, на который ссылается `Takedr1`, содержит **52 кадра**. На кадре **10**, запись Botl по `0x1074a`: type `-16`, размеры **0×0**, координаты примерно `(0.0001,0.0001)`.

`0x405064 → 0x404928` назначает эту запись именованному Botl; `0x404974` (доказательства предыдущей MULT-работы) и `0x40445c` не рисуют/не hit-test-ят растр нулевой ширины. Следовательно, по статическому пути **изображение бутылки исчезает на кадре 10**, до исполнения Addtol и State. Точное видимое время на экране не измерено. `State Botl 1` не является причиной этого исчезновения.

Дальнейшие кадры меняют также Mainhero/Main_bot: на 33–34 есть Main_bot, на 35 ему назначается пустой растр. MULT здесь — именованные обновления объектов, а не один sprite timeline героя. Если кадр не содержит Botl, это не означает автоматически вернуть старое изображение: renderer продолжает использовать последнее назначение объекта.

**Точный момент инвентаризации:** не кадр 10, не звук кадра 32 и не начало StartW. Это вызов `0x406412 → 0x40c4c4 → 0x40ec2c` после наблюдения inactive у Takedr1 и после Setxy. `Addtol` и `State` выполняются последовательно без yield между ними. Это не транзакция: ошибки/полный инвентарь не откатываются. Видимое обновление окна инвентаря происходит своим render-путём, не внутри setter.

## 8. Что потребуется TypeScript-интерпретатору

Это список механизмов, **не начатая реализация**:

1. Токеновый загрузчик SCC, включения Inc и индекс имён/ресурсов. Для строгой совместимости учитывать хеш-dispatch, регистр, scanf-порядок, сокращённую форму Click и необязательный номер сцены. Безопасно диагностировать некорректные индексы/переполнения вместо native memory corruption.
2. Реестр Handler: eventName + selectedItemId + отдельный stateObject/stateScene; не сводить два имени Botl в одно поле. Dispatch всех совпавших обработчиков, с результатом «обработан».
3. Case как индекс Program; соседние Case могут разделять один список. Break — граница списка при загрузке, не runtime opcode. Ветка выбирается по State при dispatch.
4. Контекст Program с active/waiting/mode/savedPc; немедленное исполнение до yield; кооперативный обход на тике в исходном порядке. Не заменять на `forEach(async...)` и не ждать все Start.
5. Навигационный job с точками пути, remaining/active-признаком и отдельным update; Goto сохраняет continuation и ждёт признак завершения, а не просто завершение Walk. Учесть mode=1, отсутствие пути и отмену новым кликом.
6. Анимационные jobs с loop, integer frame interval, текущим кадром, active, кадровыми звуковыми барьерами. Start неблокирующий; StartW устанавливает input-busy и ждёт active=false. Сначала resume SCC, потом animation update, потом movement update.
7. Применение MULT по именам объектов, сохранение последнего назначения, нулевые изображения и несколько объектов на кадр. Нельзя откладывать визуальное удаление Botl до Addtol.
8. Setxy как операция логической позиции героя, stop-позы, scale/преобразования, не как CSS/экранный X/Y. Математика маски/перспективы требует отдельного восстановления.
9. Объекты с независимыми State, image/frame, visibility/click-полями и координатами; State current/cross-scene и сериализация. Переход состояния не должен сам по себе скрывать sprite.
10. Инвентарь с ID, порядком слотов и отрицательным empty sentinel; Addtol немедленно пишет первый пустой слот. Явно решить совместимость с дубликатами/полным инвентарём, не выдумывать rollback.
11. Input-route: hit-test, scroll offset, выбранный item, busy-ветка, отмена текущих Program и кадрового звука. Не накапливать клики в FIFO, которой в исследованном пути нет.
12. Отдельно поддержать именованные события конца анимации (`anim+0x211`), не смешивая их с механизмом возобновления StartW.

| UNKNOWN | Все исходы повторных кликов/прерывания озвучки Takedr1 | replay с кликами во время пути, кадрового звука и после кадра 10 |
| UNKNOWN | Реальные межкадровые времена и звуковые задержки | trace tick-time, anim.frame, event latch, buffer status |

| UNKNOWN | Все error-paths отсутствующих ресурсов/полного инвентаря в UI | контролируемый replay; не менять оригинальные файлы |
| UNKNOWN | Правила всех прочих SCC-команд/валидность всех 57 сценариев | отдельные вертикальные срезы; эта работа не заявляет полного интерпретатора |

Для динамического закрытия основного пути достаточно read-only breakpoints/watchpoints в оригинальном Windows/x86 окружении:

- `0x40a238`, `0x4079ac`, `0x408cd8`: eventName, itemId, выбранное состояние;
- `0x405d30`, `0x405e5c`: Program, active/waiting/mode/pc;
- `0x409bf2`: снятие признака пути;
- `0x404fb4`: active Takedr1, кадр до/после;
- `0x405479` с Botl на кадре 10: назначение пустого растра;
- `0x406412`, `0x40ec2c`: первый фактический inventory write;
- `0x405b78`: State Botl=1.

Записать абсолютные порядковые номера тиков, а не только wall-clock timestamps. Не объявлять предложенный replay уже проведённым: в этой работе он **не выполнялся**.

## 10. Краткий ответ на вопросы исследования

1. **Click регистрируется при загрузке SCC** как Handler и таблица Program по состояниям; вызывается синхронным dispatch по имени события и выбранному предмету.
2. **Click**: itemId, eventName, stateObject, необязательная stateScene. **Case**: индекс состояния stateObject, не сравнение с первым числом Click.
3. **Последовательность внутри Program — до первого yield**; дальше polling на тике. Анимация и движение обновляются отдельно. FIFO SCC-событий в этом пути не обнаружена.
4. **Goto и StartW могут блокировать Program**; Start, Setxy, Addtol, State в бутылочном пути не делают yield. Case/Break не runtime-команды.
5. **Возобновление — повторный вход из tick**: Goto опрашивает Scene+0x72e, StartW — anim+0xbb9. Именованные события конца анимации — отдельный механизм.
6. **State хранится в объекте по +4**, setter пишет int; отрисовка/видимость/кадр — другие поля.
7. **Предмет 1 записывается после полного ожидания Takedr1 и Setxy**, до State Botl=1. Пустое изображение Botl назначается значительно раньше, на кадре 10 из 52.

Все семь ответов — выводы из статического анализа указанного SHA-256, не наблюдения запущенного оригинала.
